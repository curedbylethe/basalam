A `Tree` records which widgets exist and who is whose parent. It lives outside the widgets, so a widget never needs to know where it sits. Parent links are not part of the `Widget` interface. The tree does not store paint order or focus order.

## Why integer IDs

Salam's `dyn` values cannot be compared with `==`, and cannot be cast back to their concrete type. So "is this the focused widget?" can only be answered by position. A widget's ID is its index in the tree:

- The root is always ID `0` (`RootId`). Its parent is `NoWidget` (`-1`).
- `add` appends, so IDs stay stable for the tree's lifetime.
- A parent's ID is always smaller than its children's. That makes bubbling loop-free by construction.

## Registry order

ID order is the order widgets were added. A parent's ID is always smaller than its children's. That order is what the tree stores. It is not, by itself, paint order or focus order.

With nothing raised, the [screen](/reference/screen) paints in this ID order and walks focus in it, so a child paints over its parent and a later sibling paints over an earlier one. After `raise`, paint order is ascending `(stamp, id)` and focus stays in the topmost layer that has a focusable widget outside a hidden subtree. Stamps live on the screen, not in the tree.

```text
root(0)                added first
|-- panel(1)
|   |-- left(2)
|   `-- right(3)
`-- footer(4)          added last
```

With nothing raised, `footer` paints last and draws on top. `raise` can put an earlier id above it.

## Constants

| Constant | Value | Meaning |
| --- | --- | --- |
| `RootId` | `0` | The root widget's ID in every tree. |
| `NoWidget` | `-1` | No widget: the root's parent, and the result of a dispatch nobody consumed. |

## Tree

```salam
pub struct Tree:
    pub widgets: Vector<dyn Widget> = Vector {}
    pub parents: Vector<int> = Vector {}
end

pub func NewTree(root: dyn Widget): Tree
```

`NewTree` creates a tree whose root is `root`. A tree always holds at least its root.

| Method | Description |
| --- | --- |
| `add(parent: int, w: dyn Widget): int` | Adds `w` as the last child of `parent` and returns its ID. An invalid parent attaches it to the root. |
| `get(id: int): dyn Widget` | The widget with this ID. An invalid ID returns the root, so the call never fails. |
| `parent(id: int): int` | The parent's ID; `NoWidget` for the root and for invalid IDs. |
| `valid(id: int): bool` | Whether `id` names a widget in this tree. |
| `count(): int` | The number of widgets, root included. |
| `dispatch(from: int, event: Event): int` | Offers `event` to `from`, then to each ancestor, until one consumes it. Returns the consumer's ID or `NoWidget`. An invalid `from` starts at the root. |
| `free()` | Releases the tree's own storage. The widgets themselves are left alone. |

## Example

```salam
mut t := basalam.NewTree(basalam.BaseWidget {})
panel := t.add(basalam.RootId, basalam.BaseWidget {})
counter := t.add(panel, Counter { label = "apples" })

// Counter consumes "+", so dispatch stops there and returns its ID.
plus := basalam.Event { kind = basalam.KeyEvent, key = term.Decode("+") }
println t.dispatch(counter, plus) == counter // true

// Nobody consumes "x": it visits counter, panel, root, and comes back unhandled.
x := basalam.Event { kind = basalam.KeyEvent, key = term.Decode("x") }
println t.dispatch(counter, x) == basalam.NoWidget // true
t.free()
```

`Counter` is the widget from [Writing a widget](/guides/writing-a-widget).

<Note>
  The tree cannot remove or reparent widgets yet, because either would shift IDs. Build the tree once and change widgets' state instead.
</Note>
