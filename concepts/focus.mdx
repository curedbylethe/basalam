The focused widget receives every event first. If it does not consume the event, the event [bubbles](/reference/event#dispatch-and-bubbling) to its ancestors. While rendering, the focused widget sees `buf.focused == true` and can draw a focus indicator.

Only widgets whose `focusable()` returns `true` can take focus, and every widget on the path from that widget to the root must report [`visible()`](/reference/widget#visible) as `true`. A hidden container hides its whole subtree from focus navigation.

## The focus stack

The screen tracks focus as a stack of widget IDs. The top entry is the focused widget; an empty stack means nothing has focus, and events start at the root. A dialog such as a [Modal](/reference/modal) pushes itself here when it opens.

| Method | Effect |
| --- | --- |
| `focus(id): bool` | Replaces the top of the stack with `id`. |
| `push_focus(id): bool` | Pushes `id`, remembering the previous focus underneath it. |
| `pop_focus(): bool` | Drops the top, returning focus to what was there before. |
| `focused_id(): int` | The top of the stack, or `NoWidget`. |
| `can_focus(id): bool` | Whether `id` names a focusable widget with no hidden ancestor. |

`focus` and `push_focus` refuse IDs that are invalid, not focusable, or inside a hidden container, and return `false` without changing anything.

A focused widget that becomes hidden is revalidated by `dispatch`: after the widget chain returns, and again before the next event is routed. Focus moves to the first entry of the focus order, or clears when the order is empty.

Use `push_focus` and `pop_focus` for anything temporary, such as a dialog: push the dialog's widget when it opens, pop when it closes, and the focus goes back where it was. A [Modal](/reference/modal) opens with `push_focus` and then `raise_subtree`, and closes with `unraise_subtree` and then `pop_focus`.

```salam
if screen.push_focus(dialog):
    // ... the dialog handles keys until it closes ...
    _ := screen.pop_focus()
end
```

<Note>
  The first reachable focusable widget you `add` while nothing has focus receives it automatically, so a new screen always starts with something focused if it can. A widget under a hidden container is not reachable.
</Note>

## Two ways to move

basalam provides the movement; your application decides which keys trigger it. The library imposes no bindings, but you do not have to wire the keys by hand: the opt-in [keymap](/reference/keymap) can bind them for you.

```salam
// Opt in to the library defaults: Tab and the four arrow keys.
screen.set_keymap(basalam.NewDefaultKeymap())

// Or bind your own keys through the map.
screen.keymap.bind(term.Decode("n"), (screen: basalam.Screen*, event: basalam.Event): ret screen[0].focus_next() end)
```

Every method returns `true` when the focus moved. Each focus change queues the old bounds and the new bounds, so the next `present()` redraws those two indicators and leaves the rest of the screen.

If you would rather not write the rows, install `NewVimKeymap(on_search)` instead: it keeps Tab and the arrows and adds `h`/`j`/`k`/`l`, `gg` and `G` to the ends of the current column, all calling the same methods. [The vim preset](/reference/keymap#the-vim-preset) lists every row.

### Linear: focus_next and focus_prev

Linear navigation walks the focus order and wraps inside it. That order is the focusable widgets in the topmost raised layer, ascending ID, or every focusable widget in ID order when nothing is raised or that layer has no focusable widget. Only widgets that pass `can_focus` are candidates, so a hidden container removes its whole subtree from the order: the child of a closed [Modal](/reference/modal) is never a Tab stop. It matches paint order only while nothing is raised. Unfocusable widgets are skipped. With nothing focused, `focus_next` focuses the first widget in that order and `focus_prev` the last. A focus that sits outside the order jumps to the first on `focus_next` and the last on `focus_prev`. A raised subtree, such as an open Modal, is such a layer.

### Spatial: focus_up, focus_down, focus_left, focus_right

Spatial navigation moves to the nearest widget in a direction, chosen from the same focus order, not from every focusable widget on the screen. A hidden container removes its whole subtree from that order too, so spatial moves skip it. The search is `basalam.Nearest(from, candidates, dir)`, a pure function over rects that looks at each candidate once (O(n)); `dir` is `DirUp` (0), `DirDown` (1), `DirLeft` (2), or `DirRight` (3). With nothing focused, spatial moves fall back to `focus_next`.

## The spatial rule

A candidate qualifies only if it passes both of these tests.

<Steps>
  <Step title="It lies beyond the edge you are moving toward">
    Moving right, the candidate's left edge must be at or past the current widget's right edge. A candidate that overlaps the current widget along the direction of motion is beside it or on top of it, not to its right, so it is skipped. Touching edges (a gap of zero) qualify.
  </Step>
  <Step title="It overlaps on the perpendicular axis">
    Moving left or right, the candidate must share at least one **row** with the current widget. Moving up or down, it must share at least one **column**. A widget that is only diagonally away never qualifies, however close it is. This keeps focus moving in straight lines.
  </Step>
</Steps>

```text
moving right from F:

    +-----+          +---+        A: shares rows with F   -> qualifies
    |  F  |  gap 3   | A |
    |     |          +---+
    +-----+ +---+                 B: closer, but no shared row -> skipped
            | B |
            +---+
```

Rows and columns use the same half-open rule as `Rect`, so rects that only touch at a corner do not overlap, and an empty rect overlaps nothing.

### Ranking and tie-breaking

Among the candidates that qualify:

1. **Nearest edge wins.** The smallest gap between the current widget's edge and the candidate's facing edge.
2. **On equal gaps, best alignment wins.** The smallest distance between the two widgets' centers on the perpendicular axis.
3. **On a full tie, the earliest wins.** The candidate with the lowest ID, which is the earliest candidate in the focus order. The search does not use paint order. Once a widget is raised, paint order and focus order are not the same sequence.

```text
moving up from the wide panel W:

    +--------+ +--------+     L and R: same gap, and W's center is exactly
    |   L    | |   R    |     between theirs -> full tie -> L (lower ID) wins
    +--------+ +--------+
    +-------------------+
    |         W         |
    +-------------------+
```

Centers are compared at double resolution (`2 * x + width`) so that half-cell differences are never lost to integer division. Two candidates half a row off in opposite directions are a genuine tie, broken by rule 3, rather than one of them being misjudged as perfectly aligned.

## Showing focus

Check `buf.focused` in `render`:

```salam
pub func render(buf: basalam.Buffer, bounds: basalam.Rect):
    mut style := basalam.StyleDefault
    if buf.focused:
        style = basalam.Style { reverse = true }
    end
    buf.put_str(bounds.x, bounds.y, this.label, style)
end
```
