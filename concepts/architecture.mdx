basalam is a thin layer over Salam's `std/term`. `term` already reads keys, decodes escape sequences, switches raw mode, and builds every escape sequence basalam writes. basalam adds the structure a full-screen program needs: a tree of long-lived widgets, a single event type, a drawing surface, and a loop that ties them together.

## The big picture

```text
                    +-------------------------- Screen ----------------------------+
 terminal           |                                                              |
 --------           |   input thread              main thread                      |
 stdin   --bytes--> |   term.ReadKey  --Event-->  next_event                       |
 size    --ioctl--> |   term.Size     --Event-->     |                             |
 clock   ---------> |   tick timer    --Event-->     v                             |
                    |        (events channel)     dispatch -----> Tree             |
                    |                                |      focused widget,        |
                    |                                |      then each ancestor     |
                    |                                v                             |
                    |                             draw  -----> Widget.render       |
                    |                                |         into Buffer copies  |
                    |                                v                             |
 stdout  <--frame-- |                             present: Buffer.flush            |
                    +--------------------------------------------------------------+
```

Each box has one job:

| Piece | Job | Lives in |
| --- | --- | --- |
| [Rect and Point](/reference/rect) | Integer cell geometry. | `rect.salam` |
| [Event](/reference/event) | The one value input arrives as. | `event.salam` |
| [Widget](/reference/widget) | The five-method contract for UI pieces. | `widget.salam` |
| [Tree](/reference/tree) | Widget IDs, parent links, bubbling. | `tree.salam` |
| [Buffer](/reference/buffer) | The grid widgets draw into. | `buffer.salam` |
| [Screen](/reference/screen) | Terminal session, input thread, loop. | `screen.salam` |

## Design decisions

<AccordionGroup>
  <Accordion title="Retained mode">
    Widgets are long-lived values that keep their own state. The application builds the tree once, changes widget state, and the screen redraws. The alternative, immediate mode, rebuilds the UI from application state every frame. It suits games, but it makes focus and per-widget state the application's problem.
  </Accordion>
  <Accordion title="Only input is asynchronous">
    One background thread reads input and produces events onto a channel. The main thread consumes them and calls widgets synchronously. Widgets never run concurrently with each other or with drawing, so they need no locks, and `handle_event` is plain code. The cost is that a slow handler delays the next frame; keep handlers short and do background work in your application.
  </Accordion>
  <Accordion title="Widgets are interfaces, identified by ID">
    Any struct with the five `Widget` methods is a widget, stored as `dyn Widget`. Salam cannot compare or downcast `dyn` values, so the tree identifies widgets by integer ID: their index in the tree. IDs only grow, so a parent's ID is always smaller than its children's.
  </Accordion>
  <Accordion title="One order for everything">
    ID order is paint order (stack z-order: later widgets paint over earlier ones) and focus order. One rule instead of three keeps the core predictable.
  </Accordion>
  <Accordion title="Widgets draw into a buffer, never the terminal">
    Every widget renders into a copy of the screen's buffer, clipped to its own bounds. The copies share cell storage, so writes land in one grid. That makes rendering infallible (out-of-bounds writes are dropped), testable without a terminal, and lets the output strategy change without touching widgets.
  </Accordion>
  <Accordion title="Layout is not a widget's job">
    Widgets receive their bounds through `set_bounds`. The core's only layout rule is that the root fills the screen. Everything else is set by your application until the layout engine arrives.
  </Accordion>
  <Accordion title="No keymaps or modes in the library">
    The library delivers events and reports whether a widget consumed them. What an unhandled key means, including vim-style modes, belongs to your application.
  </Accordion>
</AccordionGroup>

## What happens to one key press

1. You press `+`. The terminal writes the byte to stdin.
2. The input thread's `term.KeyReady` returns, `term.ReadKey` decodes the key, and the thread sends a `KeyEvent` on the channel.
3. Your loop's `next_event` returns it.
4. `dispatch` offers it to the focused widget, then its parent, and so on to the root. The first widget whose `handle_event` returns `true` stops it.
5. `present` clears the buffer and calls `render` on every widget in ID order, each with a buffer copy clipped to its bounds and `focused` set for the focused widget.
6. `Buffer.flush` serializes the whole grid and writes it to the terminal in one call.

## Current limits

<Warning>
  The buffer is minimal: every frame rewrites every cell, styles are raw SGR strings, and each cell is assumed to be one column wide. Double buffering with diffing and dirty-region tracking are planned for a later release, and the `Widget.render` contract will not change when they land.
</Warning>

- The tree cannot remove or reparent widgets.
- There is no layout engine and there are no concrete widgets yet.
